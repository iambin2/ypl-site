# 디자인 방향 수립 플레이북

YPL 리디자인(2026-10)에서 디자인 방향을 정한 과정을 다른 사이트에도 쓸 수 있게 정리한 절차다. 목표는 "예쁜 시안 하나"가 아니라, **사이트의 모든 요소가 따르는 하나의 법칙**과 그것을 구현할 수 있는 기록을 남기는 것이다.

## 기본 원칙

1. **결정은 사용자가, 근거는 디자이너가.** 디자이너는 진단, 선택지, 추천과 그 이유를 내놓고 사용자가 고른다. 추천은 하나만, 이유와 함께.
2. **말이 아니라 그림으로 비교한다.** 선택지는 언제나 같은 구성의 이미지로 나란히 보여준다.
3. **모든 규칙은 숫자로.** "넉넉한 여백"이 아니라 "섹션 사이 80px". 숫자로 쓸 수 없으면 아직 정해지지 않은 것이다.
4. **실제 데이터로.** 시안에는 사이트의 진짜 이름, 기록, 문구를 쓴다. 지어낸 값은 "예시"라고 표시한다.
5. **결정은 그 자리에서 파일로 남긴다.** 채팅에만 있는 결정은 다음 대화에서 사라진다.
6. **사용량을 관리한다.** 방향을 정하는 대화는 길어진다. 구현은 새 대화에서 단계별로 한다.

## 0단계. 준비

- 프로젝트의 기존 문서(제품 정의, 디자인 문서, 작업 지침)와 사용자의 과거 피드백 기록을 먼저 읽는다.
- 과거에 거절된 방식이 있으면 확인한다. YPL에서는 "컨셉 세계관"(공항 표지판 같은 테마)이 "싸구려"로 거절된 기록이 있었고, 이후 모든 후보 평가에 반영했다.
- 무엇을 남기고 무엇을 버릴지 아직 정하지 않는다. 그건 2단계의 질문이다.

## 1단계. 현 상태 진단

실제 배포된 사이트를 열어 주요 화면 3~4개(홈, 핵심 기능 화면, 기록 화면 등)를 직접 본다. 진단은 3~4개 항목으로, 전문 용어에 쉬운 설명을 붙여 쓴다.

자주 나오는 진단 축:
- **브랜드 변별력**: 로고를 가리면 다른 사이트와 구별되는가.
- **위계**: 모든 섹션이 같은 무게로 쌓여 있지 않은가. 지금 무슨 일이 일어나는지 화면이 먼저 말해주는가.
- **핵심 자산의 대우**: 그 사이트만 가진 것(YPL에서는 실제 대회 기록)이 일반 카드에 묻혀 있지 않은가.
- **정체성 운반체**: 고유성을 실어 나를 소재(YPL에서는 포켓몬 파티)가 어디에 갇혀 있는가.

마지막에 한 문장으로 요약한다. 예: "완성도는 있지만 관점이 없는 상태."

## 2단계. 문제 정의 질문

객관식 질문 세 개를 한 번에 묻는다. 추천 선택지가 있으면 첫 번째에 두고 "추천"이라고 표시한다.

1. **리셋 범위**: 무엇을 남기고 무엇을 다시 여는가. 예: 전면 리셋, 색만 유지, 구조 계승.
2. **문제 정의**(복수 선택): 1단계 진단 항목을 그대로 선택지로.
3. **첫 화면의 주인공**: 정보 구조의 축. 예: 지금의 상태, 회원의 다음 행동, 명예와 역사, 기록 탐색.

미적 취향("미니멀 vs 화려함")은 묻지 않는다. 취향은 그림을 보고 고르게 한다.

## 3단계. 방향 후보 도출

1. **사용자 문화권에서 소재 7개를 뽑는다.** 그 사이트 사용자가 잘 아는 실물, 문서, 화면, 의식 중에서 고른다. YPL에서는 공식 대회장 서류, 스포츠 기록연감, 게임보이 흑백 화면, 팀 텍스트, 카드 게임, 중계 그래픽, 한국의 공문서와 상장이 나왔다.
2. **공감도 순으로 줄 세운다.** 7개가 최소 세 가지 재료 계열(인쇄물, 화면, 사물 등)에 걸치게 한다. 같은 계열만 나오면 더 판다.
3. **익숙한 정답을 깨는 장치를 둔다.** 무작위로 하나를 배정하거나, 외부 시각 체계를 경쟁자로 붙여 같은 정답으로만 수렴하지 않게 한다.
4. **경쟁자는 두 축으로 평가한다.** 사용자 공감도와 제품 명료성. 결과는 "이김, 경쟁, 탈락" 셋 중 하나다. 탈락한 후보도 버리지 않는다. 그 후보가 가진 규율 하나를 골라 채택된 방향에 더한다. 예: "열은 고정하고 값만 제자리에서 바뀐다."
5. **"카테고리 표준"은 언제나 출구로 둔다.** 그 업계의 정석을 최고 완성도로 하는 안이다. 디자이너가 먼저 권하지는 않지만, 사용자가 고르면 그것이 답이다. YPL은 결국 이 안을 베이스로 골랐다.

## 4단계. 한 장짜리 시안 보드

후보마다 디자인 언어 전체가 한 장에 담긴 보드를 만든다. 모든 보드는 같은 구성이어야 공정하게 비교할 수 있다.

| 영역 | 내용 |
|---|---|
| 왼쪽 | 폰 첫 화면(375 × 812). 2단계에서 정한 첫 화면의 주인공으로 |
| 가운데 | 데스크톱 대표 화면 하나(기록, 랭킹 등) |
| 오른쪽 | 디자인 언어 시트: 색, 서체, 핵심 컴포넌트, 형태와 모션 한 줄씩 |
| 하단 | 실제 데이터와 예시 데이터의 구분 표기 |

- 이미지 생성 도구가 없으면 HTML로 직접 짜고, 헤드리스 크롬으로 PNG를 렌더링한다(`--headless --screenshot --window-size=1600,1000 --force-device-scale-factor=2`). 이렇게 만든 시안은 실제 구현에서 그대로 재현할 수 있다는 장점이 있다.
- 사용자가 두 안을 섞자고 하면(하이브리드), 무엇이 베이스이고 무엇을 가져오는지 한 문장으로 정리한 뒤 같은 구성의 보드를 다시 만든다. 가져오는 것은 겉모습이 아니라 규율이어야 한다. YPL은 "카테고리 표준의 표면 + 대회장 게시지의 숫자 위계"였다.

## 5단계. 기초 체계를 하나씩 확정

방향이 정해지면 아래 순서로 하나씩 정한다. 항목마다 **비교 보드 또는 명세 보드 하나**와 **숫자로 된 규칙**을 만든다.

1. **서체**: 후보 3~4개를 같은 화면에 끼워 비교한다. 개성, 깔끔함, 로딩 방식(필요한 글자만 내려받는지), 라이선스를 함께 적는다.
2. **곡률**: 모서리 모양(원형인지 연속 곡률인지), 크기에 비례하는 반경 단계, 동심 규칙(안쪽 반경 = 바깥 반경 − 여백). 브라우저 지원을 반드시 확인한다. YPL에서는 iOS 사파리가 연속 곡률을 아직 지원하지 않아 대체 방식을 명시했다.
3. **배치와 공백**: 간격 단계(4px 격자 위 11개 값), 근접의 위계(안쪽 < 바깥, 단계마다 1.5배 이상), 격자, 배치 순서. 실제 화면에 간격 수치를 그린 레드라인 명세 보드로 보여준다.
4. **선과 면**: 어떤 선을 남기고 무엇으로 대신할지. 사용자가 "날카롭다"고 느끼는 요소는 대안을 2~3개 그려 비교한다.
5. **모션**: 눌러볼 수 있는 인터랙티브 페이지로 만든다. 정지 이미지로는 모션을 판단할 수 없다. 스프링처럼 물리값으로 정의하면 규칙이 짧아진다.
6. **나머지 영역은 한 번에**: 상호작용 상태, 깊이와 레이어, 아이콘, 숫자와 표기 형식, 이미지 처리, 피드백 상태(빈 상태, 로딩, 오류, 토스트), 반응형 구간, 접근성, 문구. 따로 정하면 규칙끼리 어긋나기 쉽다.

계산으로 확인할 수 있는 것은 계산한다. YPL에서는 연속 곡률의 45도 깊이를 원형과 맞추는 값(반경 1.6배, superellipse 1.78)과 스프링 곡선을 계산으로 정했다.

## 6단계. 디자인 법전 작성

- 위의 결정을 하나의 디자인 시스템 문서로 묶는다: 개요와 원칙, 장별 규칙, 토큰(색, 서체, 간격, 반경, 그림자 등), 핵심 컴포넌트의 실물 미리보기와 사용 지침.
- 저장소에도 사본을 둔다(예: `docs/design-system/`). 구현하는 쪽이 매번 외부 문서를 읽지 않아도 되게.
- **작성 후 자체 감사를 한다.** 모든 컴포넌트 값이 법전의 단계 안에 있는지 확인한다. YPL에서는 크기 목록 밖의 14px과 간격 단계 밖의 7, 3, 10, 26px이 나와서 바로잡았다.
- 아직 정하지 않은 컴포넌트는 목록으로 남기고, 어느 구현 단계에서 만들지 적는다.

## 7단계. 기록과 인계

방향 대화를 끝내기 전에 아래를 모두 남긴다.

| 기록 | 내용 |
|---|---|
| 제품 문서 | 확정한 방향, 서체, 곡률, 선 정책 같은 핵심 결정과 날짜 |
| 기존 디자인 문서 | "교체 중인 구 체계"라는 표시와 새 법전이 우선한다는 안내 |
| 작업 지침 파일 | 법전과 방향 계약서의 위치 |
| 방향 계약서 | 핵심 명제, 시각 세계, 사용자 흐름, 첫 화면 구성, 선택 근거, 구현 단계, 카드가 없는 컴포넌트와 담당 단계, 혼자 정하지 말고 물어볼 것 |
| 메모리 | 결정 요약, 사용자의 새 피드백, 사용량 제약 |

구현은 새 대화에서 단계별로 한다. 첫 단계는 기초(토큰, 서체, 곡률, 모션 변수)와 홈 화면이고, 끝나면 사용량을 확인해 나머지 단계를 나눈다.

## 다른 사이트에서 시작하는 법

이 파일을 그 사이트 저장소의 `docs/`에 복사한 뒤, 그 프로젝트 폴더에서 새 대화를 열고 이렇게 시작한다.

> 이 사이트 디자인을 제로부터 재검토하려고 해. docs/design-direction-playbook.md의 절차대로 1단계 진단부터 진행해줘. 전문적인 디자인 언어로 소통하되 쉬운 설명을 붙여줘.

## 이 과정에서 얻은 교훈

- 질문은 적게, 그림은 많이. 사용자는 보드를 보고 훨씬 빠르고 정확하게 결정했다.
- "전면 리셋"이라도 남길 것(색 원칙, 로고, 기능)은 질문 한 번으로 먼저 확정한다.
- 사용자의 감각적인 피드백("날카롭다", "공격적이다")은 원인 요소를 짚어 대안을 그려 보여주면 바로 규칙이 된다.
- 하나의 결정이 다른 결정을 바꾼다. YPL에서는 괘선을 없애자 하이브리드의 위계 장치가 포스터 숫자 하나로 줄었다. 바뀐 결과를 사용자에게 분명히 말한다.
- 법칙이 촘촘할수록 구현 대화가 짧아진다.
